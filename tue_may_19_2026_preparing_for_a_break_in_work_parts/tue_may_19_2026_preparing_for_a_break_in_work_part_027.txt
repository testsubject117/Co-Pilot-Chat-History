```
        Dim cleaned As New List(Of String)(lines.Length)
        For Each raw In lines
            If raw Is Nothing Then Continue For

            ' Remove ^Z anywhere in the line (some legacy files include it at EOF).
            Dim s As String = raw.Replace(ChrW(26), "").Trim()

            If s = "" Then
                ' skip truly blank lines (not a data line)
                Continue For
            End If

            cleaned.Add(s)
        Next

        ' Each entry is 6 lines
        Dim i As Integer = 0
        While i + 5 < cleaned.Count
            Dim e As New LedgerEntry() With {
                .Customer = Unquote(cleaned(i)),
                .DateText = Unquote(cleaned(i + 1)),
                .CheckNumber = Unquote(cleaned(i + 2)),
                .InvoiceDiffText = Unquote(cleaned(i + 3)),
                .Amount = ParseDecimal(cleaned(i + 4)),

        If s.Length >= 2 AndAlso
```

That is fragile, and it likely explains why one of the `7782` records is being misread or skipped.

Specifically, this part is the issue:

```vbnet
' Each entry is 6 lines
Dim i As Integer = 0
While i + 5 < cleaned.Count
    ...

End While
```

If even one legacy record in `LEDGER.CUR` is not perfectly aligned as 6 cleaned lines, then everything after that can drift out of sync.

---

## Why this matters here
Your add writer is likely writing clean 6-line records.

But the original historical `LEDGER.CUR` may contain:
- malformed legacy rows
- embedded weirdness
- extra/missing blank-ish lines
- odd quoting
- records that don’t align perfectly once `.Trim()` and blank-line skipping happen

So the parser may be grouping the file incorrectly.

That would explain why:
- one exact `7782` is visible manually in the file
- but not both are coming back as separate parsed `LedgerEntry` objects

## Most suspicious line
This:

```vbnet
Dim s As String = raw.Replace(ChrW(26), "").Trim()

If s = "" Then
    Continue For
End If
```

means you are **discarding blank lines entirely**.

But in `LEDGER.CUR`, the 4th field is often intentionally blank:

```basic
WRITE#1,N2$:WRITE#1,DT$:WRITE#1,CNUM$:WRITE#1,"":WRITE#1,CHKAMT:WRITE#1,RF$
```

So a valid record includes an empty field.

If your reader drops that blank field line, record alignment breaks. That is huge.

---

# This is the bug
The 4th field, `InvoiceDiffText`, can legitimately be blank.

But your reader removes blank lines before grouping records into 6 lines.

So this valid 6-field record:

1. customer
2. date
3. check number
4. `""` or blank
5. amount
6. reference

can become effectively **5 cleaned lines** if the blank field is written as an empty physical line or normalizes to empty after trimming.

Then every record after it can shift.

---

You should **stop removing blank lines** from `LEDGER.CUR`.

Only remove the DOS EOF marker, but preserve line positions.
